# 上下文压缩：token 预算怎么分配

> 这份文档沉淀自第 04 课（`src/04-memory`）开发过程中的一次讨论，回答一个第 04 课只在注释里
> 碰了一句、但没有展开的问题：**`TOKEN_BUDGET` 这个数字到底该怎么定？**
>
> 第 04 课演示的是「什么时候触发压缩」，本文补的是「预算本身怎么切分」。

---

## 一、先分清三个概念

新手最容易把这几个当成同一个东西，混在一起之后预算必然算错：

| 名字 | 含义 | 第 04 课对应物 |
|---|---|---|
| **上下文长度**（context window） | 模型硬上限，**输入 + 输出**的总和 | 没有出现，隐含在 `deepseek-flash` 的 1M 里 |
| **输入预算** | 窗口 − 输出预留 − 安全边际 | `TOKEN_BUDGET`（demo 里直接当了它） |
| **压缩触发线** | 涨到多少就压，通常是输入预算的 70~80% | `compactIfNeeded` 里 `estimateTokens(m) <= TOKEN_BUDGET` 的阈值 |

关键一点：**触发线不能贴着窗口边**。还要留出这一轮要生成的输出、下一轮的增量、以及
token 估算本身的误差。贴着边设，结果就是每一轮都在压。

## 二、分配单位是 token，不是条数

第 04 课里 `KEEP_RECENT = 6`（`src/04-memory/index.ts:220`）是按**条数**预留保留区的，
这是这段代码里最值得改的一处：6 条消息可能是 50 token，也可能是 5 万 token——
用户粘一篇长文档进来，保留区立刻超预算，"保留最近 6 条"这个承诺就落空了。

正确的做法是按 token 预留：

```ts
const KEEP_RECENT_TOKENS = Math.floor(inputBudget * 0.25)
```

然后从最新的 user 消息往前累加，直到凑够这个额度为止。**「切割点必须落在 user 消息上」
这条约束要保留**（`findCutPoint`，`src/04-memory/index.ts:237`）——它是第 04 课 ★ 坑 1 的解法，
保证 assistant 的 `tool_calls` 和对应的 `role:'tool'` 结果要么整组进摘要、要么整组被保留，
不会被拆散触发 400。

## 三、预算不是一个大池子，是一条优先级阶梯

真实工程里，额度是按「能不能砍」分层抢占的，从下往上砍：

| 优先级 | 分区 | 占比参考 | 说明 |
|---|---|---|---|
| 1（先扣） | 输出预留 | `max_tokens` | **不可挪用**。deepseek-flash 默认 4096 |
| 2（先扣） | 安全边际 | ~10% 窗口 | token 是估算的，必须留误差 |
| 3（硬保留） | system prompt + **工具定义** | 固定 | 每轮都发，不可压缩。装不下就该报错，而不是静默截断 |
| 4（高） | 当前轮用户输入 | 剩余全部 | 用户正在问的内容，永远优先于历史 |
| 5（弹性） | 保留区（近期原文） | 输入预算 × ~25% | 提供细节，可收缩 |
| 6（最先牺牲） | 摘要 / 更早历史 | 输入预算 × ~20% | 弹性最大 |

## 四、具体数字

以 **deepseek-flash** 为例（官方数据，也可用 `GET /models` 现查：返回
`context_window` 与 `max_output_tokens` 两个字段）：

- 上下文长度 **1M**
- 单次输出上限 **384K**（即 `max_tokens` 的上限）

```
C（上下文长度 1M）
 − max_tokens（你实际请求的值，不是模型上限）
 − 安全边际（约 10% × C）
 = 输入预算
   触发线   = 输入预算 × 0.7
   压缩目标 = 输入预算 × 0.5
```

**为什么压到 50%，而不是压到刚好过线？**

第 04 课已经有一道「压缩必须真的变小」的防线（`src/04-memory/index.ts` 里
`estimateTokens(compacted) >= before` 那个判断），但那道防线只防「白花钱」，不防「反复花钱」：
如果压到 79%、触发线 80%，下一轮加两条消息就又过线，于是每一轮都白送一次摘要调用。

留出 30% 的迟滞区间（hysteresis），才能做到「一次压缩管很多轮」。

## 五、第 04 课现存的两处缺口

### 1. `estimateTokens` 没算工具定义

```ts
function estimateTokens(messages: Message[]): number {
  return Math.ceil(JSON.stringify(toApiView(messages)).length / 2)
}
```

`toApiView`（`src/04-memory/index.ts:200`）只映射 `messages`，而 `toolDefs`
（`src/04-memory/index.ts:120`）完全没进预算。但工具定义在渲染顺序里排在最前面，
**每个请求都要发一遍**：第 04 课这 3 个小工具还好，等第 06 课接上 MCP、
工具数量涨起来之后，它就是一笔固定的、且完全不可压缩的开销
（删工具会同时破坏前缀缓存和 Agent 的行动能力）。

### 2. `/ 2` 这个启发式对 JSON 会严重低估

`JSON.stringify(...).length / 2` 对中文散文大致成立（中文约 1 字 ≈ 0.5~0.6 token）。
但工具结果是密集的 ASCII JSON——键名、引号、括号在真实 tokenizer 里大约
3~4 字符/token。同一段内容，散文和 JSON 的估算误差能差到 2 倍。

实用解法：**拿上一轮响应 `usage.prompt_tokens` 当真值基准**，只估算这一轮新增的部分。
DeepSeek 的 `usage` 还额外给了 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，
能顺便看出缓存命中情况。

## 六、隐藏成本：压缩会让前缀缓存失效

DeepSeek 的上下文硬盘缓存**默认开启**，机制是**前缀匹配**——与之前请求前缀重复的部分
按「缓存命中」计价。而 `summarizeBefore`（`src/04-memory/index.ts:255`）把
`messages[1..cut)` 整段替换成一条摘要，**前缀从摘要那一句起就全变了**，
之后所有历史都落到「缓存未命中」上重算。

所以压缩的真实成本 = 那次摘要调用 + **下一轮全量未命中的差价**。

单价（元 / 百万 tokens，deepseek-flash）：

| | 空闲时段 | 高峰时段 |
|---|---:|---:|
| 输入 · **缓存命中** | 0.02 | 0.04 |
| 输入 · **缓存未命中** | 1 | 2 |
| 输出 | 4 | 8 |

命中 / 未命中 = **1 : 50**。推论：

- **压缩要少而狠**（一次压到位），不要频繁而轻压——后者会把之后每一轮都拖下水。
- 还要权衡「后面还剩几轮」：压一次的成本 ≈ 被压区大小 + 摘要大小，
  收益 ≈ 之后每轮省下的 (被压区 − 摘要)。**只剩一两轮就结束时，压缩是纯亏的。**
- 能挪到空闲时段跑的多轮任务，成本直接砍半。

（注：DeepSeek 的硬盘缓存没有 Anthropic prompt caching 那种「写缓存加价」，
所以这里的成本几乎全部来自「重写前缀后那一轮的全量未命中」。）

## 七、可选的改进清单

如果要把第 04 课按本文改一遍，改动都在 `src/04-memory/index.ts` 单文件内：

1. `KEEP_RECENT` 从「按条数」改成「按 token」预留
2. `estimateTokens` 补上 `toolDefs`
3. 加迟滞区间（触发线 ~80% / 压到 ~50%）
4. 摘要那次调用加 `thinking: { type: 'disabled' }`——它本来就不带工具，思考纯属浪费
